Task2View pilot: architectural views from a request and a repository

Pilot study, October 2026: 2 Java repositories × 10 prompts, one run per condition, model Claude Sonnet 5.5. Diagrams are from runs on 2026-10-13.

The Task2View pipeline

Purple badges are steps that call a language model; green badges are deterministic code. Everything the model says about the code is checked against the code before it is drawn.

Inputs: a request (one prompt, in the stakeholder's words) + a repository
Stage 1 · Understand the request
0Repository cardcode

Parse the repository once, with no model.

  • symbol table (tree-sitter): classes, methods, packages
  • code dependency graph
  • entry points, entities, database and deployment facts
→ repository card
1Read the requestLLM · 1 call

Work out who is asking and what they need to see.

  • role (e.g. developer, tester, DevOps), target feature, detail level
  • view spec: scope, granularity, structure and/or order of calls, notation
  • up to 3 clarification questions (defaults in batch runs)
→ stakeholder profile + view spec
2Choose the viewscode

Pick at most 3 viewpoints that together cover the needs.

  • covering selection over the Views & Beyond catalogue
  • role priors from V&B Table 9.1
  • one slot for behaviour when the request asks how parts interact
→ view plan
3Architectural questionscode

Each view gets the questions it must answer.

  • from the request's needs and subjects
  • e.g. 'which parts take part in booking a seat?'
→ questions per view
▼
Stage 2 · Collect evidence from the code
4Plan the investigationLLM · 1 call per view

Decide where in the code to look for each view.

  • seeds from the repository card
  • one task per view
→ investigation tasks
5Evidence agentLLM + repository tools

Read the code and make claims that cite it.

  • each claim cites file, lines and symbol, and names the question it answers
  • every claim is checked by code: excerpt matches, lines and symbol exist
  • claims that fail the check are dropped
→ evidence model (verified claims)
6Decide per viewcode

Is every question answered by verified evidence?

  • draw · ask for one more evidence round · simplify · declare a gap · drop
→ decision per view
▼
Stage 3 · Build the architectural view
7Abstract into partscode + 1 naming call

Turn classes into the parts an architect would draw.

  • classes grouped by architectural role: UI, API, service, domain, data access, database …
  • arrows lifted from code dependencies; dependencies against the layering flagged
  • the model only names and describes parts; code checks the names
  • one set of parts per request, shared by its views
→ architecture model (parts + connectors)
8Drawcode

Each view in the notation of its viewpoint, for its reader.

  • decomposition, layered → UML packages
  • uses → UML «use» dependencies
  • client-server and other C&C → C4 components
  • sequence, data model, deployment, use case → UML
  • overview readers (managers, customers) → plain boxes and arrows
→ diagram (PlantUML / Graphviz)
▼
Stage 4 · Check and deliver
9Check the viewcode · no LLM judge

Three questions, answered by rules.

  • true to the code? every part's classes exist, every arrow has code evidence
  • readable? no method names on arrows, few crossings, short box text, title and legend
  • matches the spec? granularity, scope, view type, notation
→ validation report
10Outputcode

A folder per request.

  • README with the views and decisions
  • diagrams + architecture.json (parts with their classes)
  • traceability to files, usage and cost
→ run folder
Output: 1–3 architectural views, each traceable to the code

The three conditions

  • Plain agent: Claude Code (Sonnet 5.5) in the repository, given the stakeholder's request and asked for architecture views as PlantUML.
  • Skill agent: the same, with the Task2View skill installed (the Views & Beyond catalogue and the method as instructions), so the agent follows the method itself.
  • Task2View: the pipeline above, run end to end.
