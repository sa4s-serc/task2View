Task2View: phase-by-phase inspection

2026-10-26. Based on the 10 runs on this site (simplified pipeline, one view per request), the code, the earlier design docs, your observations and the expert feedback from the email thread (numbered E1–E25 below). Every finding was checked against the run files or the source code; opinions are marked as such.

Short answers to your questions

Is "component view" not the right view? It is the right view; the pipeline got it wrong. Phase 1 has no need called "component", so the model mapped "high-level component view" to decomposition. A component-and-connector view was a candidate but lost a tie-break. Nothing maps a requested diagram type (component, sequence, deployment, use case) directly to a view: 3 of the 4 short requests got the right view only because their words matched the catalogue's descriptions.
Does the knowledge make sense for choosing the view? Mostly not. Of 23 needs, 30 viewpoints and 13 roles, the 10 runs used 11 needs, 6 viewpoints and 5 roles. The role priors (from V&B Table 9.1) changed the chosen view in 0 of 10 cases. Need names ("collaboration", "actors-goals", "interaction-order") are catalogue words, not what stakeholders say. Seven component-and-connector viewpoints overlap, and ties are settled by catalogue order.
Is the repository card iffy? Yes, in specific ways. Its basics are right (all classes, layers, REST routes, entities, database settings check out), but it finds no Swing screens in either repository, the text version the model reads cuts key facts (12 of 19 entry points; the Report entity's links), embeddables are listed as tables, entity subclasses show no fields, and the "most depended-on" ranking puts a UI styling class above the main facade.
Can evidence collection be made better? Do the GR10-Q1 replies make sense? The GR10-Q1 claims are true but do not fit the request: the agent is told to claim classes, then the code throws class identity away and rolls them up into four package boxes. One relation is reversed and mistyped ("SystemServicesController is-part-of UserRegistrationController"). Verification only checks that cited lines exist: 0 of 221 claims were rejected and 201 are "observed", so it confirms citations, not claims. Phase 5 is 86–93% of each run's cost, with prompts growing to 50–80k characters because whole files are read.
Should the evidence model be the same for a repository whatever the task? I think yes. Today it is not: between requests on the same repository the claimed classes overlap only 0–20% (GR10) and 10–78% (Progetto-IS), so names and parts change with the wording of the prompt. That is exactly the coupling you saw: a more detailed prompt gives more subjects, which give more questions, more agent steps and finer grain. The docs never weighed a per-repository model and rejected it; it came from ADR-005 (choose the viewpoint before the questions) and the Phase 4 redesign (one task per view and subject). Your own literature report recommends "one model, views as queries over it". Risk: a generic model may miss a specific call path, so keep an on-demand trace for sequence views.
Abstraction and the cap? The repository is literally organised as Boundary/Control/Entity/Database, but abstraction classifies by class-name endings first, so it invents "Presentation/Application/Domain/Data access", draws false "against the layering" arrows and hides the booking-rule classes (Strategy) as helpers. The cap cuts in list order, not by importance: GR10-Q4 drops 5 of 8 use cases; the sequence view drops all 9 alternative fragments; short requests always get the smallest cap because "complete" or "the functionalities" don't count.

Phase by phase: input, output, problems

Phase 0 · Repository card (code)

Input
the repository
Output
files by class, classes (symbols), dependency edges, entry points, entities, deployment and build facts, layers, signals; a 40–48-line text card for the model
  • Verified correct: all classes, BCED layers, 14 REST routes, 4 main methods, @Entity sets, JDBC URLs; 10 of 10 sampled edges true.
  • No screens found: only classes that extends JFrame count, but these apps create JFrames inside other classes (~10 GR10, 13 IS screens missed). .form files are classed "other" and cannot be read by the agent.
  • Text card truncates every list at 12 and entities at 8 fields: IS shows 12 of 19 entry points (no StudyRoomController routes, no Login/Registration mains); GR10 Report loses its links to Citizen and operator.
  • @Embeddable types (Credentials, Location) listed as tables; entity subclasses (Citizen, Student) shown with no fields and no extends User.
  • "Most depended-on" counts repeated calls, not distinct callers: WizardStyle (UI style) ranks above LibraryFacade.
  • No primary entry point (IS Launcher). Noisy lines: raw Python dicts, internal signal names, fully qualified names everywhere.
  • Unused: card notes, layer dict, file line counts, all signal evidence; several signals never fire.

Phase 1 · Read the request (model, 1 call)

Input
the request + a 10–11k-character prompt (23 needs, 13 roles, an example)
Output
role, target, needs with quotes, subjects, detail level; view spec; clarification
  • Short requests → 1 need, 1 view, 1 question. Long requests → 3–6 needs, 2–13 questions (36 in total for the six).
  • No view-type vocabulary: "component view" → decomposition; "dynamic view" worked only because the model inferred interaction-order. (E25)
  • "software analyst" matches no role (analyst = security/performance). Role priors never changed a choice.
  • Detail level is decided by counting needs/subjects: "a complete deployment view", "the functionalities of the system" → overview → smallest cap.
  • Clarifications are never answered (defaults); for the IS-seat requests code overrides the model's default to "both" and adds an order-of-calls need that the single view then cannot show.

Phase 3 · Choose the view (code) and Phase 2 · Questions (code)

Input
needs, repository signals, catalogue
Output
one viewpoint + rationale + uncovered needs; template questions per (need, subject)
  • Ties between overlapping viewpoints settled by "frames vs also-covers" and catalogue order (invisible to a stakeholder).
  • Needs only table viewpoints frame (ownership, rationale, variability) can be extracted but never shown.
  • One view per request loses the dynamic view: all five long IS requests lose the order of calls; IS-seat-L2/L3 lose change impact; GR10-Q3 loses dependencies. This conflicts with the expert's advice to give a static and a dynamic view (E3, E14, E19).
  • Questions are near-identical templates (IS-reg-L3: 5 decomposition questions differing only in the subject); an order-of-calls subject was filed under decomposition.

Phase 4 · Investigation plan (model, 1 call) and Phase 5 · Evidence agent (model, 3–7 turns)

Input
questions + text card; tools: list, read, search, symbol, neighbours
Output
claims (elements, relations, call steps), each citing file, lines and code
  • GR10-Q1: 13 claims, all true, but at the wrong grain: classes, while the view rolls them into package boxes. Entities claimed as "components". Boundary covered by 1 of 9 GUIs, Control by 2 of 10 controllers. One reversed, mistyped relation.
  • IS-reg-L1: correct call chain, but only StudentFactory (the librarian branch is lost); thrown exceptions modelled as messages; REST and Swing entry points mixed in one scenario.
  • GR10-Q4: actor–use case links right; "Register" missing; "Log in" has no actor; the same file read 3 times.
  • Cost: Phase 5 = 86–93% of each run; prompts grow 8k → 50–80k characters (whole files read; old results never trimmed; no cache hits).
  • Task-dependent: claimed classes overlap 0–20% between GR10 requests, 10–78% between IS requests. (E20, E21)

Verification and evidence model (code)

Input
claims + repository card
Output
accepted/rejected claims; elements, relations, scenarios
  • Checks only that file, lines, excerpt and symbol exist. 0 of 221 claims rejected; 201 "observed". It does not check that a responsibility is true, a relation's direction or kind, or relevance.
  • "observed" is decided by name matching in the excerpt; non-code elements default to observed; use-case links are always "inferred". The labels carry no information.
  • Card facts (all entities, states, artifact, datastore) are added to every model whatever the request.
  • Evidence model and view disagree on layers (ReportService: domain in the model, application in the view).

Abstraction into parts (code + naming call) — structural views

Input
evidence model + dependency graph
Output
parts with member classes, arrows lifted from code, names
  • Ignores the repository's own BCED layering (name suffix beats package): entity registries become "data access", so intra-Entity calls are drawn red "against the layering"; layers are renamed. (E8, E9)
  • Booking rules (AssignmentStrategy, FirstAvailableAssignment) classed as helpers and not drawn — the very classes IS-seat-L2/L3 want to change.
  • DTOs and off-topic classes inside parts; role labels ("Web client, User interface") shown as if they were classes; orphan parts with no arrows; arrow labels are fixed templates ("reads and saves"), not observed intent. (E10, E12, E13)
  • Subject splits and naming-call splits are mostly undone by the cap, or produce single-class parts (IS-reg-L3 is a class diagram with renamed boxes). (E22)

Phase 7 · Draw (code) — caps and projection

Input
parts, or the evidence model for other views
Output
one UML diagram (PlantUML)
  • Caps set in 3 places (pipeline.yaml max_parts 7/9/9; viewpoints.yaml max_elements per family and level; a hidden minimum arrow weight of 3) and applied in ~8 places. They cut in list order, unranked.
  • GR10-Q4: 5 of 8 use cases dropped; Municipal Operator left with one. IS-reg-L1: one lifeline cut (a gap in message numbers) and all 9 alt fragments dropped, so error paths look like the normal flow. GR10-Q3: the enums asked for are not drawn and not listed. GR10-Q1: the database is silently left out. (E7, E15, E16)
  • Sequence labels are full signatures and exception texts; returns drawn as solid calls; use-case diagram has conflicting layout directions. (E5, E11)

Phase 8 · Check (code)

Input
the drawn view + evidence model
Output
verdict
  • Checks only "compiles" and "every mark is backed by a verified claim". Any limitation gives "pass with limitations": 8 of 10 views. The verdict carries no signal.
  • Misses: cut elements the request asked for, orphan parts, wrong layering, PNG vs JSON mismatch, arrow meaning. (E6)

Cross-cutting: why a detailed prompt makes everything more complicated

  • Detail level = number of subjects in the request → more questions (1 vs up to 13) → bigger agent budget (12/16/20 steps) → class grain → more claims and splits → more parts → more is cut by the cap. The request controls the content of the model, not just the choice of view.
  • Because the evidence model is rebuilt per request, the same system gets different parts and names for different stakeholders (0–20% overlap on GR10).
  • Docs are stale after the 23 Oct simplification: README still lists reconciliation.json and "five-layer validation"; ADR-006 still says 3 views, Phase 6, a judge; ADR-007 still mentions the judge; the paper's method section describes the old pilot pipeline.

What I would change (opinion), in order

  1. One repository model, built once (cached per repository): packages/layers as the repository has them (BCED here), components, dependencies, entities, deployment, and the main call paths per entry point. The request then only chooses the view, the scope and the level of detail. This removes Phase 2, most of Phase 4 and the per-request agent, and makes names consistent.
  2. Phase 1: read the view type first. Map explicit words ("component view", "sequence/dynamic view", "deployment view", "use case diagram", "class/data model") straight to the UML diagram; use the needs catalogue only when no type is named. Allow a static + dynamic pair when the request asks for both (the expert's advice).
  3. No caps on enumerations the request asks for (use cases, entities, enums); rank before any cut; keep alt fragments whenever their messages are drawn.
  4. Fix the card: detect screens by new JFrame, stop truncating, drop embeddables, show inheritance, rank by distinct callers.
  5. Simplify abstraction: one part per repository package/layer (fall back to roles only without packages); no subject or naming splits; keep the naming call for names only; drop DTOs.
  6. Sequence views: method names only, dashed returns, alt fragments for error paths.
