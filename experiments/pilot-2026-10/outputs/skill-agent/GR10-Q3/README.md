## Goal
> I am a database engineer. I need to modify the persistence layer to support future changes to the management of municipal reports. Before modifying the database, I need to understand the main data entities stored by the system, the relationships among them, and which information must be persisted throughout the lifecycle of a report. In particular, I need to understand how users, reports, locations, categories, states, state changes, internal notes, and notifications are related, and which parts of the application depend on this persisted information.

## What the evidence says about the persistence model
Tables: `users` (Citizen, MunicipalOperator), `reports`, `status_updates`, `internal_notes`, `notifications`. Schema is generated by Hibernate (`hbm2ddl.auto=update`) against MySQL `reports_db`; no SQL script exists.

| Subject | Persisted as |
|---|---|
| users | `users`: user_id PK, name, lastName, phone_number, email (unique), password, role discriminator |
| reports | `reports`: report_id PK, title, description, category, report_date (DATE), attached_image, current_status, citizen_editable, citizen_id (not null), operator_id (nullable) |
| locations | embedded in `reports`: city, cap, street, street_number, municipal_area (all not null) |
| categories | enum `ReportCategory` stored by name in `reports.category` (5 values) |
| states | string `reports.current_status` (submitted, assigned, in_progress, resolved); no state table or enum; state objects are transient and rebuilt on load |
| state changes | `status_updates`: update_id, update_date, new_status, report_id, operator_id |
| internal notes | `internal_notes`: note_id, text, created_date, report_id, operator_id |
| notifications | `notifications`: notification_id, sent_date, message, notified_status, citizen_id, report_id |

Lifecycle facts to preserve: a report is created as `submitted` with citizen_editable=true and no operator and **no** status_updates row; each transition (submitted→assigned→in_progress→resolved) sets the operator, updates current_status/citizen_editable and appends one status_updates row; notifications are written only for `assigned` and `resolved`; internal notes can be added at any time by an operator.

### Who depends on what (access matrix, from `ReportService` / `UserService` via `PersistenceService`)
| Entity | ReportService | UserService |
|---|---|---|
| User / Citizen / MunicipalOperator | findById (User, MunicipalOperator) | save, findByFields (credentials.email/password), findById |
| Report | save, update, findById, findByFields | none |
| StatusUpdate | findByFields (history); written by cascade on update(report) | none |
| InternalNote | findByFields; written by cascade on update(report) | none |
| Notification | save, findByFields | none |

Controllers reach persistence only through these two services (V2). Queries use attribute-name strings (`citizenReporting.userId`, `report.reportId`, `location.municipalArea`, `currentStatusName`, `category`, `credentials.email`): renaming a mapped field or column breaks them without a compile error.
