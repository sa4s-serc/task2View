A stakeholder asked for an architecture view of a software system. Work out the inputs of that view yourself, so
that the stakeholder only has to confirm them. Fill in every field below: take it from the request where the
request says it, and otherwise infer the most likely value from the request and the repository summary.

Fields:
{questions}
- entity: the system in one line (what it is and who uses it), from the repository summary.
- focus: the part of the system the view should concentrate on, in one plain sentence (for example a feature, a
  kind of user or an area of the code), or "the whole system".

For "aspects", give every concern at least one option id.

Then say where you are unsure. A field is unsure only if the request gives no basis for it, or if two readings of
the request would lead to different views. List each unsure field under "unsure" with one plain question to the
stakeholder (no architecture terms). Fields that can be unsure: focus, stakeholder, perspective, detail_level,
concerns. If you are sure of everything, leave "unsure" empty; the views are then drawn without asking.

Write at most {max_extra} extra questions, and only for something the fields do not cover that would change which
view is drawn or what it contains. If there is nothing, write none. Each is one plain sentence, with the reason it
matters ("why") and, where the repository summary shows the possible answers, up to four options.

Repository summary:
{summary}

Request (verbatim):
{request}

Reply with only this JSON:
{{"entity": "...", "focus": "...", "stakeholder": "...", "perspective": "...", "concerns": ["...", "..."],
  "detail_level": "overview" | "balanced" | "detailed",
  "aspects": {{"<concern, exactly as in concerns>": ["<option id>", ...]}},
  "unsure": {{"<field>": "<question to the stakeholder>"}},
  "extra_questions": [{{"question": "...", "why": "...", "options": ["...", "..."]}}]}}
